# 2026-08-22 router.php パフォーマンス改善と計測

対象ブランチ: `performance-up-thread`
作業ブランチ: `performance-up-thread-opt`（未コミット）

結論から書くと、**PHPのホットパスから約1,270ns/パケットを削減し、スループット +18.2%、転送1GBあたりのCPU時間 -28.1%** となった。
あわせて、**これまでの計測手順にカーネル転送が混ざる問題**が見つかったので、そちらを先に記す。

---

## 1. 計測環境の問題（最重要）

memo.txt に記載の

```
echo 1 > /proc/sys/net/ipv4/ip_forward
```

を router コンテナで実行すると、**PHPルータではなくカーネルがパケットを転送してしまう**。
docker-compose.yml は意図的に `net.ipv4.ip_forward=0` を設定しているので、この行を実行してはいけない。

### 根拠

| 確認内容 | 結果 |
|---|---|
| `ip_forward=1` + PHPルータ**停止** で alice → bob に ping | 疎通する（ロス0%） |
| `ip_forward=0` + PHPルータ**停止** で alice → bob に ping | 100%ロス（正しい状態） |
| `ip_forward=1` + PHPルータ**起動** で ping | 応答が `(DUP!)` になる ← カーネルとPHPの二重転送 |
| `ip_forward=1` + PHPルータ**停止** で iperf3 TCP | **4.81 Gbps**（カーネル単体の性能） |

### 影響

同じ `performance-up-thread` のコードで測ったスループット:

| 条件 | 結果 |
|---|---|
| `ip_forward=1`（カーネル転送が混入） | 2.99 Gbps |
| `ip_forward=0`（PHPルータのみ） | **2.09 Gbps** |

memo.txt の「performance-up: 2.47Gbps」「performance-up-thread: 3Gbps」「performance-up-all-in-thread: 2.6Gbps」も、
同じ手順で測っていたなら過大評価になっている可能性がある。**再計測を推奨。**

### 計測前のチェック

```bash
docker compose exec router sysctl -w net.ipv4.ip_forward=0
# PHPルータを止めた状態で ping が 100%ロスになることを必ず確認する
```

参考値として、この環境でのカーネル転送は 4.81 Gbps（retr=0）。これが実質的な上限。

## 2. 見つけたバグ: 自NIC発パケットの判定が常にfalse

`Router::start()` の判定が hex文字列とバイナリを比較していて、**一度も成立しないデッドコード**になっていた。

```php
$srcMac = unpack("H*", substr($pkt, 6, 6))[1];   // → "c22b94fda983" (12文字のhex文字列)

if ($srcMac === $Device->getBinaryMacAddress()) {  // → 6バイトのバイナリ。絶対に一致しない
    echo "same data nic";
    continue 2;
}
```

バイナリ同士の比較に修正した。ついでに毎パケットのhex変換（`unpack("H*")`）も不要になった。
なお、ここにあった `echo "same data nic";` はホットパス上の無バッファ出力で、
もし判定が成立していたらスループットを大きく落としていた。あわせて削除。

## 3. 改善内容

### 3-1. IPヘッダチェックサムを差分更新にする（最大の効果）

TTLを1減らすと、IPヘッダ中の16bitワードがちょうど `0x0100` 減る。
1の補数和の性質から、**チェックサムに `0x0100` を1の補数加算するだけ**でよい（RFC 1624）。
20バイトを `ord()` で舐める10回ループが消える。

```php
$cksum = (ord($data[24]) << 8) | ord($data[25]);
$cksum += 0x0100;
if ($cksum > 0xFFFF) {
    $cksum = ($cksum & 0xFFFF) + 1;   // end-around carry
}
```

呼び出し元で EtherType=0x0800 を確認済みなので、TTLは offset 22、チェックサムは offset 24-25 に固定で決まる。
IHLのパースもVLANの多段スキップも不要（VLANフレームはそもそもここに到達しない）。

### 3-2. フレーム全体の余分なコピーを1回削る

改修前は `IpPacket::decrementIPv4TtlAndFixChecksum($dstPkt)` に渡していたが、
**別関数に値渡しすると参照カウントが増え、関数内の1バイト書き換えで1514バイトのコピーがもう1回走る**。

`substr_replace()` の戻り値は refcount=1 なので、同じ関数内でバイト書き換えまで済ませればコピーは発生しない。
そのため TTL/チェックサムの処理を `createDestEtherFrame()` 内に畳んだ。

```php
$dstPkt = substr_replace($data, $dstNewMac . $this->devMacBin[$devIdx], 0, 12);
// ここで refcount=1 なので以下はコピーなしのin-place書き換え
$dstPkt[22] = chr($ttl - 1);
$dstPkt[24] = chr($cksum >> 8);
$dstPkt[25] = chr($cksum & 0xFF);
```

### 3-3. Deviceのゲッター呼び出しをやめ、intの平坦な配列に前計算

パケットごとに `$Device->getIpAddressLong()` などを呼んでいたのをコンストラクタで展開。

- `Device::$ipAddressLong` / `$netMaskLong` の型を `string` → `int` に修正
  （`ip2long()` の戻り値intが string プロパティに代入されて文字列化しており、
  `in_array()` の比較のたびに型ジャグリングが発生していた）
- `in_array($x, [$a, $b])` は毎回配列を確保するので `===` の2連結に
- ブロードキャスト判定はNICに依存しないのに NICループの中にあったので、ループの外へ出した
- ネットワークアドレス `ip & netmask` もコンストラクタで計算済みにした

### 3-4. IPアドレスの long2ip / ip2long 往復を廃止

`long2ip($ip["dst"])` で文字列にしてから `getNextHopByTargetIp()` の中で `ip2long()` で戻していた。
転送処理は最後までintのまま扱い、**文字列化はARP未解決時（初回のみ）に限定**した。
ARPキャッシュのキーもintにしたので、文字列キーのハッシュ計算もなくなる。

### 3-5. ARPキャッシュにバイナリMACを保存する

`Arp::sendArpRequest()` は `unpack` の `H12` でhex文字列を返すため、
転送のたびに `macToBinary()`（`str_replace` + `pack`）を呼んでいた。
**キャッシュ格納時に一度だけバイナリ化**して、以降はそのまま使う。

### そのほか

- 転送できないパケットで例外を投げていたのをnull返しに変更（例外オブジェクトの生成コストを回避）
- ループ内の `$this->` プロパティ参照をローカル変数に退避
- `getNextHopByTargetIp()` はメソッド呼び出しを削るため `start()` 内に展開

## 5. エンドツーエンド計測（iperf3 TCP）

### 条件

- `iperf3 -c 10.0.1.10 -P 2 -t 10`（alice → bob、routerコンテナのPHPが転送）
- `ip_forward=0` を毎回検証してから計測
- ARP解決とキャッシュのウォームアップのため、1回目の計測は捨てる
- 順序による影響を排除するため **A/B → B/A** の順で各3回、計6回ずつ
- CPU時間は `start_eth0.php` プロセスの `/proc/<pid>/stat` の utime+stime 差分

| 指標 | 現状 | 改善版 | 差 |

スループットは実行ごとのブレが大きいが、**CPU秒/GB はブレが小さく明確に分離している**
（現状 5.48〜5.64、改善版 3.77〜4.48）。PHP側の効率改善はこの指標に素直に出ている。

## 6. 正しさの確認

改善版で以下を確認済み。

- `ping -c 3` → TTL=63（1回だけデクリメント）、ロス0%、`(DUP!)` なし
- `ping -c 3 -s 1400` → ロス0%
- `iperf3 -u -b 500M -t 5` → **215,791パケット中ロス0（0%）**

カーネルはIPヘッダチェックサムが不正なパケットを黙って捨てるため、
UDPで1パケットも落ちていないことが、差分更新チェックサムが全パケットで正しいことの証明になる。

## 7. 今後の方向性

memo.txt の `strace` 結果のとおり、**write 66% / recvfrom 33%** とsyscallが支配的。
PHP側を1,270ns/パケット削っても効果が+18%に留まるのはこのためで、
これ以上はPHPコードを削るより **syscallの回数を減らす** ほうが効く。

- `sendmmsg(2)` / `recvmmsg(2)` で数十フレームを1回のsyscallにまとめる
  - PHPのsocket拡張は未対応なので FFI が必要
- `PACKET_MMAP`（AF_PACKETのリングバッファ）でコピーとsyscallを削る
- カーネル転送の 4.81 Gbps が、この環境での現実的な上限の目安
